# Purr

Purr is a single-process terminal app for reviewing GitHub pull requests with Claude. Reviews run as Claude Agent SDK sessions, one per PR, in the background. You drive everything from a keyboard TUI (and, planned, by voice with Pipecat; see Voice), and nothing is posted to GitHub or merged without your explicit approval.

Purr's win is organizing PRs: reviews start on their own for what's assigned to you, and you always know what's waiting on you and what isn't, across repos. Inside a PR, it feels like Claude Code on purpose.

Command: `purr`. Python package: `purr` (check availability on PyPI before publishing).

## Problem

Juggling several PR reviews inside the Claude Code terminal gets messy. It's hard to see which reviews are in flight, find the one you were working on, and resume it (`/resume` doesn't solve this well). Purr makes PRs the primary unit: every PR has its own review session, state and findings, and getting back to any review is one keypress. Stepping away makes it worse: when you come back, there's no quick way to see what finished, what failed and what's waiting on you.

Purr should feel like Claude Code, but organized around PRs: your repos and their PRs are the home screen, and inside a PR you're in a Claude Code-style session for that PR.

## Goals

- See all relevant PRs in one place, grouped by review state, across all the repos you work on.
- Start reviews with no typing: mark PRs and press one key, or assign yourself on GitHub.
- Run many reviews concurrently without disturbing the user's working copy.
- Resume any PR's review session at any time, including after restarting the app.
- Inside a PR, work as you would in Claude Code: a full conversational session in the PR's worktree.
- Catch up after being away: what happened to each PR since you last looked at it is news (bold titles, the top bar, `ctrl+n`), and what needs you is first in the list.
- Move between repos and PRs instantly, and notice when something happens in another repo. Everything should feel fast.
- Control everything by keyboard, and later by voice, interchangeably.
- Never take a visible action on GitHub (comments, review verdicts, merges) without approval.

## Non-goals (for now)

- GitLab (design so it can be added later, but GitHub only for v1).
- Android app. Long term, it would talk directly to the voice agent. Not in scope.
- Remote access when the app is closed. Like Claude Code remote control: app not running means nothing to connect to.
- Reviewing the PRs you're only asked to look at, or the whole team's: only PRs assigned to you are reviewed on their own (see Triggers).

## Architecture

One Python asyncio process (`app.py` puts it together) containing these Pipecat workers, all on Pipecat's in-process worker bus (`AsyncQueueBus`), sharing a single `WorkerRunner`:

1. **`github`** (`workers/github.py`): polls GitHub, keeps the PR list, reads replies to you, and does every GitHub write you approve (posting, assigning, merging).
2. **`git`** (`workers/git.py`): Purr's own clone of each repo, local diffs, and the PRs' worktrees.
3. **`lead`** (`workers/lead.py`): plans each review (depth, priority, focus) and starts it.
4. **`reviews`** (`workers/reviews.py`): one Claude Agent SDK session per PR, run as a task each, a few at a time; everything you say in a PR's conversation goes through it.
5. **`suggestions`** (`workers/suggestions.py`): suggests what you might ask next in a PR's session.
6. **`activity`** (`workers/activity.py`): records events in the activity log, and logs them.
7. **`upnext`** (`workers/upnext.py`): what's up next in each watched repo's pool (see Up next).
8. **`tui`** (`tui/bridge.py`): the Textual app's seat on the bus. The voice agent will be another (see Voice).

The **SQLite store** (`store.py`) is shared by all of them. (Pipecat Subagents has been merged into Pipecat core as `pipecat.workers` / `pipecat.bus`, available since `pipecat-ai` 1.16.0; the standalone `pipecat-subagents` repo is archived.) Workers talk in two ways (see Bus messages): **jobs**, typed requests one worker answers (Pipecat job coordination), and **events**, broadcast to everyone. The TUI is a bus participant, as the voice agent will be, so starting a review will be the same path from either: send a job, listen for events.

Why not proxy agents or Redis: we looked at Pipecat proxy agents and they are point-to-point tunnels between two named agents. Only targeted messages of allowed types cross; broadcast messages (like "review finished") are not forwarded. Since everything now lives in one process, the local bus is enough. If components are ever split into separate processes, switch to a shared distributed bus (e.g. Redis), not proxies.

Relevant docs (verify current APIs before building):
- Workers and the runner: https://docs.pipecat.ai/pipecat/learn/your-first-agent
- Multiple workers on one bus: https://docs.pipecat.ai/pipecat/learn/multiple-llm-agents
- Job coordination: https://docs.pipecat.ai/pipecat/learn/job-coordination
- Proxy agents (for background on why we're not using them): https://docs.pipecat.ai/pipecat/learn/proxy-agents
- Claude Agent SDK for Python (`claude-agent-sdk`). It comes with its own Claude Code (the CLI, in the package's `_bundled/`), which it runs each session on, so Claude Code needn't be installed. It uses Claude Code's login (shared, in `~/.claude`) or `ANTHROPIC_API_KEY`; `purr login` logs in with the bundled one (`claude auth login`). What you run yourself (`c`, `purr login`) is your own `claude` if it's on your PATH, else the bundled one (`purr/claude.py`).

## Repos

One Purr instance covers several repos; you don't run one per repo:

- PRs assigned to you, asking for your review, or that you took part in can be in any repo, and Purr tracks all of them (see Triggers).
- One process means one list of what needs you (and later one voice agent and one push-to-talk key). A Purr per repo would split "what happened" across windows, and compete for the microphone.
- It's the first goal: all relevant PRs in one place.

Two things keep this cheap:

- **Watched repos** (the ones whose pool you see) are added and removed in the UI, and there are none to start with. Running `purr` inside a checkout opens that repo directly (see TUI), so the Claude Code habit of starting inside a repo still works; if the repo isn't watched yet, Purr offers to add it.
- **Purr's own clones.** Purr keeps a blobless clone of each repo with open PRs in its data dir (`repos/<owner>/<name>.git`) and creates review worktrees from it. Your checkouts are never touched (no extra worktrees, refs or fetches in them), and PRs assigned to you in repos you don't have locally work the same way.
- **Open PRs are synced into the clone, so diffs are local.** The `git` worker syncs on start, and a second after the PR list changes (a poll found new or updated PRs), batching whatever else changes in that second, in the background:
  1. One `git fetch` for the PRs that are new or have new commits (`refs/pull/N/head` → `refs/purr/pull/N`) and the branches they merge into (`refs/purr/heads/<base>`; the poll now carries each PR's `baseRefName`). PRs no longer open lose their ref.
  2. A commit-graph, so finding where each PR branched off takes ms instead of 50.
  3. The files those diffs touch, in one more fetch: their blob ids come from the trees (`git diff --raw`, no contents needed), and only missing ones are requested.

  Nothing new, no network (bases are refetched every 10 minutes regardless). The diff is then `git diff <base>...<head>` in the clone, the same as GitHub's, with no 300-file or 20,000-line limit. Measured on pipecat from scratch: the clone and first sync of 337 open PRs took 19 s in the background, the clone is 31 MB, and a diff over the bus takes 7 ms on average (23 ms for a 3,000-line one). A PR the clone doesn't have yet (a push since the last sync, a repo still cloning) gets its diff from GitHub instead.
- **A worktree only once a review starts.** Diffs don't need one. Starting a review (`r`, or auto-review) makes the PR's worktree, where the agent, and you through the PR session or `c`, can run the code and change it. It's made from what the sync already brought, so there's no fetch unless the PR moved since, or the default branch was last fetched over 10 minutes ago. Measured on pipecat: the first worktree takes 3 s (the clone downloads the rest of the repo's files once, ending at 61 MB), the next ones 1.4 s and 0.2 s.
- **Where they are, and using one yourself.** `~/.local/share/purr/worktrees/<owner>/<repo>/<number>` (under the data dir), shown in the PR's header while it's there (`Worktree ~/.local/share/purr/worktrees/pipecat-ai/pipecat/6940`). `!` opens your `$SHELL` there, making the worktree first if the PR has none (not reviewed yet, or removed); exit it to come back to Purr, which keeps running underneath.
- **Your changes are never thrown away.** A review turn on the same head leaves the worktree as it is, with whatever you (or the agent, with your OK) did there: changes, commits on top of the PR's head, a rebase (to push, see Pushing), a rebase or merge stopped on a conflict. Each worktree keeps the head Purr last put it on in a ref of its own (`refs/worktree/purr/head`), so it knows the PR hasn't moved even when what's checked out isn't on top of it, as after a rebase. (A worktree from before that is left as it is if what's checked out is the head or on top of it.) When new commits move it on, uncommitted changes go to a stash first (`git stash list` there: "purr: changes in owner/repo#N at abc1234, before def5678"). A worktree with uncommitted changes is never removed.
- **What git left halfway is undone when it's in the way.** The agent can be stopped while a rebase, merge, cherry-pick or revert is stopped on a conflict. On the same head, it's left for the agent to finish. When the worktree has to move, git can't stash unmerged files (it once failed with `could not write index`, every turn after). So before moving a worktree, Purr aborts what's halfway (`git rebase --abort`, …: `_unfinished` in `git.py`), which puts it back where it began, often the PR's head already.
- **Worktrees go when they're done.** A PR's worktree is removed when you approve the PR through Purr, and when it's merged or closed; after the first poll on startup, those left from before go too, if their PR is unknown, no longer open, or approved by you (`GitWorker.sweep`). Never while a review is running in it. Nothing is lost: Claude Code keeps the session under `~/.claude`, not in the worktree, and finds it by path even with the directory gone. A follow-up, a re-review, `c` or `!` (the `GetWorktree` job) makes it again at the same path, and the session carries on.

## PR states

| State | Meaning |
|---|---|
| **Not reviewed** | The pool: open PRs in watched repos that nobody is reviewing (no assignee). Also PRs assigned to you that haven't been reviewed yet (with auto-review off). |
| **Reviewing** | A review session is running, or the lead is planning a first review. |
| **Needs you** | Reviewed, and waiting on you: a proposal to decide, a question from the agent, or your verdict. Or someone answered you on GitHub since your last word there (see Replies). |
| **Done** | You gave your verdict, and nothing else is pending. |

Done means you gave your verdict: you approved the PR or requested changes, at its current head (or merged it, and it's gone), through Purr or on GitHub. Nothing else counts. Purr keeps your latest verdict on each PR (`prs.verdict`, `prs.verdict_head`): it's set when Purr posts one, and read from GitHub along with the replies (`verdict_of` in `github.py`: your last review that approved, requested changes or was dismissed, and its commit; a dismissed one leaves none). A read begun before Purr posted one doesn't undo it. When a verdict you gave on GitHub is of the PR as it is, what the agent proposed to approve it or request changes is dismissed as moot; its other proposals still wait on you. A posted comment, a dismissed proposal or a follow-up that ends without proposing anything leaves the PR in Needs you, since you haven't said where it stands. With nothing else waiting on you there (`No verdict yet`), `a` approves it: the decision box says `[a] approve PR`, and Purr posts an approval of its head as if the agent had proposed one (`ApprovePR`); to request changes, ask the agent. A verdict is of the commit it was given at: after new commits, the re-review brings the PR back to Needs you, and you give it again. The rule is `Store.resting_state`, which both the review and GitHub workers settle a PR with once nothing's under way on it. PRs left done without a verdict by the rule before (nothing left to decide was enough) need you again once Purr starts.

"Needs you" is pinned to the top of the list. Right under it, **To merge**: Done PRs you approved as they are (your verdict's head is theirs) that are still open, with a `⇡` mark and no note, since the group says what they wait for (`to_merge` in `tui/lists.py`). They're done, since you gave your verdict, but merging is next and in Done they're easy to forget; once merged or closed they're in Done. The home screen counts them per repo too (`TO MERGE`). **Waiting on author** is the same for PRs you requested changes on as they are (`waiting_on_author`, a `↩` mark): your part's done, but the PR isn't. Polls read what changed on it (every minute): a reply to you brings it back to Needs you (see Replies), and so do new commits (`_back_to_you` in `workers/github.py`, noted `New commits since your verdict`), since your verdict was of what it was; with auto-review, the lead also re-reviews them. **Done** is what you finished: PRs you reviewed that were merged or closed (whatever still waited on you then: a proposal on a merged PR is moot, so its decision box doesn't show, `a` does nothing and `r` won't review it; `closed` notes one closed without merging). It comes after what's asked of you (Review requested, Up next) and before what others are reviewing and the pool of unreviewed PRs (hundreds, in a big repo), so what you finished lately is at hand: the latest 5, by when they got there (`prs.state_at`, which moves when the state does, and when the PR is merged or closed), with `/` finding the others; an older one you go to (an alert, `ctrl+p`, a search) shows too while it's selected. PRs someone else is assigned to aren't a state of their own: they're grouped as **Others reviewing**, after Done, with who has them, so you can see what's under way and taken. PRs asking for your review by name (see Triggers) aren't a state either: not reviewed yet, they're grouped as **Review requested**, after Reviewing, apart from the pool.

## Triggers

Two ways in, same result:

1. **From GitHub**: assign yourself to a PR on the web, in any repo (watched or not). The poller (every ~60 s, through `gh`) notices, and the lead plans its review and starts it (with `auto_review`, on by default). Polling, not webhooks, because the app runs locally.
2. **From the app**: select a PR to read its description, files and CI first, then press `r` (or mark several and press `r`). The app dispatches review jobs **and assigns you on GitHub**, so teammates see you've taken it. On a PR someone else has, `r` asks first and adds you next to them. The PR is *Reviewing* from the moment the lead starts planning its review, and you're assigned once the review starts. Assigning you first would put the PR in *Not reviewed* for those seconds (it's yours, with no review yet), so the list would jump there and back. If the review doesn't start (`esc` while it's planned, say), the PR goes back to *Not reviewed*.

Every PR assigned to you gets reviewed. No team-wide auto-review: only PRs explicitly assigned to you (avoids burning tokens on PRs others handle). How deep each review goes, what it focuses on and what goes first is up to the lead (see The lead); both ways in go through it.

**Review requests don't start a review**, only assignment does; otherwise Purr would review far too much. They're shown, though: requests for your review by name (GitHub's `user-review-requested:@me`, in any repo; team requests don't count) are news ("asks for your review") and sit in their own group, **Review requested**, so the PRs the core team was asked to look at stand apart from the rest of the pool. `r` reviews one and assigns you, as anywhere.

**The pool** ("Not reviewed") is the open PRs in the watched repos that nobody is reviewing. Starting a review assigns you, and teammates assign themselves when they review, so "nobody is reviewing it" simply means "no assignee". A PR leaves the pool as soon as someone is assigned (it moves to "Others reviewing") or it's closed. Drafts aren't listed, and neither are your own PRs (see below).

**Polling** uses GitHub's GraphQL search through `gh`, batching every search into one request per page. Each watched repo has one search: its open, non-draft PRs by other people, with author, opened date and assignees, which splits into the pool and "Others reviewing". It stays lean on purpose (pipecat: 337 PRs in 4 pages). Adding descriptions and file lists made a 100-PR page take 5.8 s instead of about 2 s, so those are fetched when you look at a PR (see Repo screen). A search takes 1-2 s regardless of size, and a big repo's pool is several pages (pipecat: 4), so a repo is fully synced only on startup, when added, and every 15 minutes. Polls in between fetch just the PRs updated since the last sync (5 minutes of overlap for search-index lag), which is usually one request of about a second. The search index also lags behind pushes. Right after a push it can still report the head from before, which would look like new commits. So when the search says a reviewed PR's head moved, Purr reads the head from the PR itself before believing it (`moved_reviewed` in `sync.py`; one request for all of them, with the PRs gone from the searches). A newly added repo's pool is shown page by page as it arrives. A search that fails or comes back incomplete never removes anything. Results are kept by repo and number (`_Search.found`): a search across repos finds a #1 in each of several, and keeping them by number alone once made your PRs' search look incomplete on every poll, so merged and closed PRs were never noticed. Nor does a search reopen a PR Purr has as merged or closed: GitHub's search lags, and right after you merge a PR (with `m`, say) it can still list it as open and assigned to you. Such a PR's status is looked up with the rest (`not_open`, `Store.closed_among`), and only if it says the PR is open (reopened) is it open again, quietly. Besides the repos' searches, every poll runs four across all repos: PRs assigned to you, PRs asking for your review (each PR's search result carries its review requests, so a request made or withdrawn shows up in the incremental updates too), and PRs by others you've commented on or reviewed (`commenter:@me`, `reviewed-by:@me`), for replies to you.

**Your own PRs aren't Purr's.** Purr is for reviewing others' PRs: you work on yours elsewhere (in Claude Code, say), and GitHub tells you when someone comments on one. No search lists them (`-author:@me` in each, but the requests for your review, which never ask you about yours), so they're in no group, counted nowhere, and bring no repo to the home screen; a database from when Purr had them loses them (the migration that drops `prs.authored`), and `auto_answer` in an old `settings.toml` is ignored.

**Replies.** Once you've reviewed a PR, through Purr or on GitHub (any open PR by others you've commented on or reviewed, in any repo: `prs.involved`, which sticks), Purr keeps an eye on the other side of the conversation: after a poll, it reads the comments on those PRs that changed on GitHub (on the first poll after startup, all of them; batched, 20 PRs to a request of about half a second), and works out what was said to you since your last word there (`replies_to` in `github.py`):

- on the PR itself, anyone's comments after anything you said on it;
- in a review thread you're in, anyone's comments after your last one in it, or after your last word on the PR (a comment, or a review that says something or decides; one that's only replies in other threads doesn't answer this one);

Bots (Codecov, CI) don't count, and nothing does until you've said something. A PR with replies you haven't answered **needs you**: it moves from Done to Needs you, it's news ("alice replied"), and its pane shows them, the latest three, under the transcript where proposals go: who, where (`bus.py:42`) and what. `x` says they need no answer (the ones seen so far: `prs.replies_done_at`); answering on GitHub, or posting a proposal through Purr, answers them. Either way the PR goes back where it rests: Done if you gave your verdict on it as it is, Needs you if you haven't, Not reviewed if Purr never reviewed it. Something else may still need you (a proposal, a failed review, an agent at work). PRs you only took part in are tracked quietly: not news, and their repo isn't listed at home, until someone replies. Replies are kept per PR (`prs.replies`, JSON), and the next read replaces them. Writing to the PR's agent while replies wait (a new turn, not while it's working) carries them along in a note (a `<purr-note>`, which the transcript leaves out), since a comment on the PR is in no review thread it can read, so "answer alice" works.

## The lead

An agent that thinks about what needs doing before the review agents start: `LeadWorker` (`workers/lead.py`) on the bus, with the planning itself in `lead.py`. It **never skips a PR**: everything assigned to you gets reviewed, and every review ends by saying plainly whether it found something.

- **What it decides, per PR** (a `ReviewPlan`):
  - *depth*: **quick** for small, low-risk changes (docs, typos, bumps, tests only, small obvious fixes): one agent reads the diff and the code it touches, no subagents, on a cheaper model (`quick_model`, Sonnet by default). **Full** for anything with real risk: the repo's review skill when it has one (pipecat's `code-review`), with subagents for independent checks, on the review model. When in doubt, full. Your own messages in a PR's session get the review model, even after a quick review: that's where you dig in. A model you chose for the PR (`/model`) wins over both.
  - *priority*: high, normal or low: the order reviews wait in line. High when someone's likely waiting (small fixes, release labels, PRs you asked for); low for drafts, failing CI, big PRs that take long anyway.
  - *focus*: up to 4 points specific to the PR for the review to look at hardest, naming a repo skill when one fits ("docstrings and changelog: pipecat:prose-review").
  - *why*: one line for you, shown under the PR's status.
- **When it runs**: after every poll, for the open PRs assigned to you that were never reviewed (on startup, once the first poll is in), and when a PR gets assigned to you; all at once, so one call plans a poll's worth (batches of 15). **Re-reviews are planned too**: new commits on a reviewed PR assigned to you go to the lead with what changed since the last review (the new commits' subjects and the files they touch, from the clone: commits and trees only, `GitRepos.new_commits`), so a small follow-up ("Address review: guard the race") gets a quick look and a rewrite gets a full one. A quick re-review doesn't follow the repo's review skill; the plan replaces the review's (`reviews.plan` is the latest round's). `r` in the TUI (one PR or several marked) asks it too (`PlanReviews {prs, depth}`), and those are always high priority, since you're waiting.
- **How**: one tool-less Agent SDK call with structured output (`lead_model`, Sonnet by default), from each PR's description, files with +/- lines, CI and labels (fetched from GitHub as it plans) and its earlier review; the repo's skills (only those a review agent can load are offered for focus) and its review skill; your review and code style. Measured on pipecat's 10 most recently updated PRs: 12 s and $0.05 for all ten. It called the 50-line flow-config fix and the Sarvam error fix quick, the 3,000-line Sidechat feature full and low priority, the SyncParallelPipeline frame-routing fix full and high, and the regex fix with failing CI quick and low, with focus points like "can a turn be dropped or the LLM answer twice; hold_secs timer cancellation on interruption".
- **Never in the way**: if it can't plan (offline, a bad answer), or leaves a PR out, the PR gets a full review anyway (`by: default`, with the reason). The PR shows "Planning the review" meanwhile.
- **What stays in code**, not up to the lead: nothing is posted without you, the permission policy, how many reviews run at once, budgets.
- The plan goes to the review worker with `StartReview {pr, plan}` (or `Rereview {pr, plan}` for new commits), is stored with the review (`reviews.plan`, JSON), rides on `review.started`, and goes into the review agent's system prompt ("How this review should go"), so follow-ups know it too.
- The same planning is what the voice agent will use ("what should I look at first?", "give #3112 a full review"); pipecat 1.16's `LLMWorker` (a bus worker with `@tool` methods) is the shape for that.

**Found something or not.** Every finished review says one thing first. **Only issues count**: suggestions and nits are mentioned, but a review with nothing else found nothing (`found 1 issue, 2 nits`, `nothing found (2 nits)`, `nothing found`). In the PR list, a reviewed PR's mark says it at a glance (✓ green: nothing found; ● red: found issues), except where its group says more: To merge (⇡), Waiting on author (↩) and Done (✓ green, whatever its review found: you've finished with it), and Needs you, where every PR needs you all the same: there the mark is ⚠ (✗ red if its review failed), and a dim note after the title says what for, the most pressing first, as the decision box asks (`needs_you_for` in `tui/session.py`): the agent's question (`Asks: $ uv run pytest`), its proposal by what `a` would do (`Request changes?`, `Approve PR?`, `Post comment?`, `Push?`), your comments (`Post your comments?`), replies (`alice replied`), `Review failed`, or `No verdict yet`; the PR's header says it in words, and how deep the review went (`● Full review: found 1 issue · 1 pending action`); while a review waits or runs, the lead's plan is under it (`Planned: a full review, high priority. Core pipeline frame routing fix`); alerts and news say `review: nothing found` / `review: found 2 issues`. Finding nothing is a fine outcome, and the review agent is told so.

## Up next

The pool can be hundreds of PRs. Rather than you choosing, the lead suggests a few worth looking at next in each watched repo: small and straightforward, in code you know. They're the **Up next** group in the repo's list (after Review requested), best first, each with why after its title, dim; the PR's header says it too (`➜ Up next: Small fix to Deepgram's reconnect; you've reviewed 8 PRs there.`), and home counts them (UP NEXT). `r` takes one as any other.

- **What it goes on** (`purr/upnext.py`), worked out without asking anyone: each pool PR's size, from Purr's clone (`GitRepos.numstat`: `git diff --numstat`, the blobs the sync already brought); whether it's in folders you've worked in, from your latest 50 merged PRs and 50 you reviewed in the repo, with their files (`GitHub.history`, one request per repo every 6 hours, about 7 s for pipecat; folders more than a third of them touched, like `changelog/` and `tests/`, and the top one, say nothing and are left out); whether you've reviewed its author's PRs; and how long it's waited. Small and familiar count most (`score`). The best 15 are the shortlist, each with its reasons in words (`small (12 lines)`, `in services/deepgram, where you've been in 8 PRs`).
- **The lead chooses** from the shortlist: one tool-less structured call on the lead's model (`lead_model`), with your review style, choosing `up_next` of them (5) and saying why in a line each. **Up next stays full** while the pool has enough: what the lead leaves (all of it, if it can't say: offline, a bad answer) is filled from the top of the shortlist, with its reasons (`fill`).
- **`s` skips one** that isn't for you (the key shows only on Up next PRs): it leaves Up next for good (`SkipUpNext {pr}` on the upnext worker; the `up_next_skipped` table, which keeps its title and author), the cursor goes on to the next PR, and the lead is asked again at once to fill its place. **It learns**: each time, the lead is told what you skipped lately and the PRs you took (others' PRs you had reviewed there, latest first), next to your review style, and chooses accordingly.
- **When**: when the PR list changes and after the clones sync (`git.synced`, which the git worker sends after each sync), for each watched repo, asking the lead again only when the shortlist changed: at once when Up next is short (you took one, or skipped it), else not more than every 10 minutes per repo. A PR that's taken (assigned), reviewed or closed leaves Up next at once, and another takes its place a few seconds later. Only what changed is drawn again. It's kept in the `up_next` table, replaced as a whole each time.

## Review workers

- One task per PR in the `reviews` worker, wrapping a Claude Agent SDK session.
- Each review runs in its **own git worktree** (made from Purr's own clone of the repo, see Repos), checked out at the PR head, so multiple reviews run concurrently without touching each other or the user's working copy.
- Persist the SDK **session ID** per PR in SQLite so any review can be resumed (from the PR session, or after an app restart). Closing the app pauses running reviews; they resume on reopen.
- The SDK keeps each session's transcript (it's a Claude Code session file); that's what sessions resume from and what the PR pane loads, with `get_session_messages(session_id, directory=worktree)`. Purr also records every conversation in SQLite as it happens (`runs` and `messages`, see SQLite store), with times, for analysis.
- Output of a review:
  - A short summary.
  - A list of findings (with file/line where possible, severity: issue / suggestion / nit).
  - A **pending action** proposed by the agent: a GitHub review to post (e.g. "post 3 comments + request changes", "approve"). Merging is never proposed: it's yours (see Merging).
- The agent must **never** post to GitHub or merge directly. All GitHub-visible actions, pushes included, are proposed as pending actions and executed by the app only after user approval. Enforced, not just prompted: Claude Code deny rules plus a PreToolUse check deny GitHub writes (`gh pr review|comment|merge`, `gh api` with a write method, `git push`; see Permissions), and the agent gets a `propose_action` tool to use instead.
- The user can keep working in a PR's session after the review; see PR session.

How it's built (`src/purr/review/`, `src/purr/workers/reviews.py`):

- The agent reports through in-process tools (`review/tools.py`): `submit_review {summary, findings: [severity, text, file?, line?]}` and `propose_action {kind: request_changes|approve|comment, description, body, comments: [path, line, body], replies: [thread_id, body]}`, plus `get_review_threads`. A new proposal (or a new review) dismisses the previous pending one.
- The session ID is a UUID Purr picks before starting, stored right away, so even a review that dies early can be resumed (`resume=`), or restarted under the same ID if no transcript was written yet.
- **Permissions** are Claude Code's own; see Permissions.
- Only the user's own Claude Code settings are loaded (`setting_sources=["user"]`). A PR's `.claude/settings.json` could define hooks, and hooks run commands.
- The repo's own skills, agents and commands (`.claude/skills`, `.claude/agents`, `.claude/commands`) are loaded from its default branch as a plugin named after the repo, so pipecat's show up as `pipecat:code-review`, `pipecat:docstring`, ... (`plugins=`). Purr builds it from its clone (`git archive` of those directories into `plugins/<owner>/<name>/<key>`, the key coming from their tree hashes), so it's rebuilt only when they change on the default branch. Frontmatter that could get around the review policy is dropped: `hooks`, `allowed-tools`, `permissionMode`, `mcpServers`. The repo's `settings.json` isn't used. A review goes ahead without them if they can't be loaded.
- **The repo's own review skill.** When a repo has a skill for reviewing PRs, Purr's full reviews follow it (quick ones don't) (`review/skills.py`). pipecat's `code-review` is one: its multi-agent process (CLAUDE.md compliance, two bug scans, each issue validated by another agent) and its bar (only high-signal issues) replace Purr's general guidance.
  - *Which skills:* those whose name says "review" or whose description says they review PRs ("code review", "review a pull request"). A skill with both is clearly the one; for pipecat that's `code-review`, while `prose-review` is only a candidate and `cleanup`, `pr-description` aren't.
  - *Choosing:* one clear skill is used without asking, and a notice says so. Otherwise, if there are candidates, Purr asks once (a dialog listing them, plus "Purr's own review"), and the repo's reviews wait up to `permission_wait` (5 minutes) for the answer, then go ahead without it; `esc` means ask again next run. The choice is kept per repo (`review_skills` table: the skill or '' for Purr's own, who chose it, when). `i` then `s` inside a repo changes it. A skill the repo later drops means Purr's own review.
  - *How:* the review starts with the skill as a slash command (`/pipecat:code-review <PR URL>`), the way you'd run it in Claude Code. That works for skills marked `disable-model-invocation` too, which the agent couldn't start on its own. A section in the system prompt fits the skill into Purr: skip its checks on whether to review at all (draft, already commented on by Claude), never post (what it would post goes into `propose_action`; the policy denies `gh pr comment`/`gh pr review` regardless), and finish with `submit_review` and `propose_action`. Re-reviews of new commits follow the skill's process again. Each review records the skill it followed (`reviews.skill`), so reviews with and without a skill can be compared (cost, turns, what got approved).
  - Subagents the skill starts (pipecat's starts about eight) are recorded in `messages` like everything else, tagged with the call that started them; the PR's conversation shows only those calls (`Agent(Scan for obvious bugs)`) and what each came back with.
  - Any other skill can still be run by hand in a PR's session: type `/pipecat:prose-review`.
- PRs assigned to you are reviewed automatically (`auto_review`, on by default), through the lead (see The lead): when a poll reports an assignment, and after every poll for any open PR assigned to you that was never reviewed. On startup that means once the first poll has brought the store up to date (the GitHub worker announces each finished poll with a `github.synced` event), not from what the store remembers, which may be a PR that closed or was reassigned while Purr wasn't running. Reviews interrupted by quitting resume on the next start.
- **A few at a time.** At most `max_reviews` (3) reviews run at once, re-reviews of new commits and resumed reviews included; the rest wait in line by the lead's priority, then in order (`workers/slots.py`), and their PR's pane says where they are (`Queued, next up`, `Queued, 2 ahead`). Your own messages in a PR's session don't wait: you're the one waiting for them.
- A failed review moves the PR to Needs you, with the error.
- **`esc` stops the agent**, as in Claude Code, while it's doing something on the PR (reviewing, waiting its turn or for you, answering you, or the lead planning its review), from the PR's pane, where you follow it (`PRSession`'s binding, only while there's something to stop, so the footer says `esc Stop` then and the working line `esc to stop`). Not from its prompt, where `esc` goes back to the pane: Claude Code stops from the prompt, but in Purr you press `esc` to leave it, and doing so once stopped a rebase halfway, leaving the worktree in a conflict. Nor from the list or the diff, where `esc` goes back (home, after `r` in the list, would otherwise stop the review just started), nor while the pane is zoomed: `esc` zooms out first. The `StopAgent` job cancels the run's task (which closes the SDK client and the CLI with it), and the run is recorded as failed, `Stopped by you`; what you wrote that it didn't read isn't sent after it. A turn in the conversation (your question, a re-review) just ends: `◼ Stopped` in the thread, the review stands and the PR goes back where it was. A review you started over gives way to the one before it (`drop_review`): that one's conversation is back, and what it proposed, which starting over had set aside, waits for you again. A PR's first review stays, cut short (`◼ Review stopped · r to review it` in the header), and the PR is *Not reviewed* again; the lead doesn't start it again by itself, only `r` does. Stopped while the lead's still planning it, it doesn't start (the review worker refuses it for the next 3 minutes, as long as planning can take).
- **Starting a review doesn't zoom**: after `r` (or `/review`) the list stays next to the PR's pane and the focus where it was, to start the next one right away. `z` puts the PR's pane full screen to follow it. Only the diff opens full screen.
- **`r` on a PR whose review finished asks first** ("reviewed already. Review again, from the start?"), since it sets what was proposed aside and starts a new session.
- The agent reads linked issues (`gh issue view`) to know what the PR is meant to do, and the PR's existing review threads (a `get_review_threads` tool: ids, file and line, resolved or not, comments, with the user's own marked) so it doesn't repeat what's been said. A proposal can carry `replies` to existing threads next to its new inline comments; Purr posts the review, then the replies. A reply failing after the review went up is a warning, not a retry, so the review can't be posted twice.
- **New commits** on a reviewed PR assigned to you (with `auto_review`): the same session gets a follow-up asking it to look at `git diff <reviewed head> <new head>`, say which earlier findings are resolved or still stand, reply on the threads about them, and propose what to post now. Each review records the commit it last looked at (`reviews.head_sha`). The agent remembers its first review, so there's no interdiff machinery: the conversation is the memory.
- Measured on a 44-line pipecat PR: about 75 s from start to proposed action, including the first blobless clone of pipecat (about 7 s).

## PR session (Claude Code inside a PR)

Opening a PR (`enter`, or `tab` to its pane) puts you in a Claude Code-style terminal for that PR. It's the same Agent SDK session the review ran in, working in the PR's worktree, so you pick up where the review left off: ask questions, ask it to dig deeper, run the tests, or change its proposed action.

- Looks and behaves like Claude Code: streamed assistant messages, tool calls collapsed to one line (`⎿ Read(src/bus.py)`), the prompt at the bottom with history, and the most useful slash commands.
- The prompt takes several lines: `enter` sends, and `ctrl+j` starts a new line (so do `shift+enter`/`alt+enter` in terminals that tell them apart, and a `\` at the end of the line, as in Claude Code). Pasting keeps the lines.
- **Suggestions, like Claude Code's.** Once the agent's done, the empty prompt shows what you might ask next, dim (`Is the race on shutdown real?   (tab)`); `tab` or `→` puts it in the prompt to send or edit, and typing anything else hides it. Claude Code makes these itself (`--prompt-suggestions`, a `prompt_suggestion` message after each turn), but they're gated per account (a tryout got none, from the SDK or `claude -p`) and the Python SDK drops message types it doesn't know, so Purr makes its own: a tool-less structured call (`purr/suggest.py`, `suggestion_model`, Haiku by default) that reads the PR, what waits on you, and the end of the conversation (your messages, the agent's text, its review and proposal; not tool calls or reasoning, 12,000 characters at most). It's asked for once per point in the conversation, only for the PR you're in (focus in its pane, the agent idle, nothing to answer), so skimming PRs with `n`/`p` costs nothing; a suggestion that doesn't come is none.
- It works like a shell's: `↑`/`↓` on the first/last line go through what you asked on this PR, `ctrl+r` searches everything you've asked on any PR (type to filter, `enter` puts it in the prompt), and Emacs's keys move around and edit (`EmacsArea`, `tui/editing.py`, which the comment editor and the file editor are too): `ctrl+a`/`ctrl+e` (the very start and end of the line), `ctrl+b`/`ctrl+f`, `alt+b`/`alt+f`, `ctrl+p`/`ctrl+n` (as `↑`/`↓`: the box takes them over from the app while it has the focus), `alt+<`/`alt+>`, `ctrl+k`/`ctrl+u`/`ctrl+w`/`alt+d` kill and `ctrl+y` yanks what was killed last, `ctrl+_` undoes; `ctrl+space` sets the mark, and moving then selects from it (`ctrl+w` kills what's selected) until you type. `esc` or `ctrl+g` lets go of a selection (the mark's, or a `shift` one) before doing what it does otherwise. The comment editor is the same box (and `ctrl+g` cancels it, as `esc` does, once nothing's selected). `page up`/`page down` scroll the transcript while you type. What you ask is kept in the `prompts` table, so the history survives restarts.
- History comes from the SDK's transcript of the session; new turns stream over the bus as `session.message` events, so the TUI and (later) the voice agent see the same conversation.
- One conversation per PR. What you write goes into the same session (the `SendMessage` job), straight away even while the agent works (see below).
- **Slash commands** (`tui/commands.py`). Typing `/` lists what matches above the prompt (Purr's commands, Claude Code's useful ones, the repo's skills; after three letters, by what's in the name too, so `/prose` finds `/pipecat:prose-review`): ↑/↓ pick, tab or enter fills it in, enter again runs it.
  - *Purr's own*, handled by Purr, never sent to the agent: `/help` (all of this, with the repo's skills); `/review [quick|full]` (start over with a fresh review, planned by the lead, at the depth you say if you do; `/clear` is the same, so Claude Code's `/clear` can't cut the session off from Purr); `/model [name|default]` (the model for everything in this PR's conversation, stored with the PR, so it sticks, unlike Claude Code's `/model`, which Purr would override on the next turn); `/cost` (each run on this PR: what it was, when, how long, turns, tokens, cost, model, and the total, from the `runs` table); `/shell` (same as `!`); `/claude` (same as `c`); `/theme [name]` (the theme picker, as `i` then `t`; with a name, that theme, kept in `settings.toml`). Their output goes in the transcript, just for you.
  - *Passed to Claude Code as typed*: `/compact` and `/context`, the repo's skills (`/pipecat:prose-review`), and anything else after a `/`, your own skills included.
- **Open in Claude Code** (`c`, or `/claude`), in a sentence: the PR's conversation is a real Claude Code session that Purr shows in its own, simpler view; `c` opens that same conversation in Claude Code itself, in the PR's worktree, for what Purr's view doesn't do (rewind, plan mode, pasting images, interrupting with esc, its diffs of edits). Quit it to come back (`/exit`, which a line printed before it starts says). It's for hands-on work, so the key isn't in the footer. How it works is at the end of this section.
- Same guardrails as the review: anything GitHub-visible becomes a pending action.
- **Writing while the agent works** goes to it straight away, as in Claude Code: it reads it at its next step (Claude Code absorbs it mid-turn), or as a turn of its own while its background agents are out. Each run has an inbox the review worker puts your messages in, and the run sends them into the live session (`client.query`). That takes knowing when the run is really over, which a result doesn't say (a turn ends, but background agents, or your message, may still be owed a turn): Purr sets `CLAUDE_CODE_EMIT_SESSION_STATE_EVENTS`, and the run ends when the CLI reports `idle` after a turn's result, with nothing of yours unsent or not yet taken up. A message sent just as it went idle waits for the CLI to take it up (`running`). From a CLI that reports no state, messages wait in the inbox, and whatever's left when a run ends goes as a follow-up. Claude Code stores what it absorbed mid-turn as an attachment (`queued_command`) that the SDK's session reader leaves out, so reloading reads those from the session file and puts them back after the message they followed. A slash command can't go in while the agent works (`Busy`): it stays in the prompt until it's done.
- **Deciding happens in the conversation, not in per-finding cards.** You keep digging with the agent until you agree on what to post; "drop the nit", "reword the race comment", "make it a comment instead" make it propose again, and the new proposal replaces the old one. Writing while a proposal waits sets it aside straight away (as `x` would), so what's on screen is never a proposal the conversation has moved past; your message carries a note for the agent (a `<purr-note>`, which the transcript leaves out) saying so, and to propose again, changed or as it was, if it still recommends posting something. The thread says so (`◼ Proposal set aside: …`, then your message), also when reloaded, from the note. Slash commands (`/compact`, a skill) aren't replies and leave it be. The transcript shows each proposal in full (verdict, overall comment, every inline comment and thread reply), so `a` posts exactly what you've read.
- Permission prompts: when Claude Code asks about a tool call, the prompt shows inline as in Claude Code (`a` allow once / `A` always / `x` deny, the same keys as approving or dismissing a proposal) and the PR moves to **Needs you**. See Permissions for `A`. Writing instead is a no with directions, like Claude Code's "No, and tell Claude what to do differently": the tool call is denied with your message, the agent reads it there and carries on in the same run, and the thread shows it under the call: `⎿ Not allowed: you wrote instead`, then your message. The agent waits up to `permission_wait` (5 minutes) and then carries on without it, saying at the end what it wanted to run and why. The wait has to be bounded: Claude Code gives up on an unanswered permission request after about 10 minutes, and after that its session refuses every tool call.
- The agent's reasoning shows in the transcript the way Claude Code shows it: dimmed, ahead of what it leads to, a line per thought (its heading or first sentence: `Checking the lock file…`). In full, even summarized, it's about ten times what the agent says (measured: 137k characters of thinking to 14k of replies), so `t` shows it in full only when you ask, and again a line each on the next `t`. Purr asks for summarized thinking (`thinking={"type": "adaptive", "display": "summarized"}`); the SDK's default returns it empty.
- `z` zooms the session to full screen and `esc` zooms out; unzoomed, `esc` leaves the prompt, and from the pane stops the agent while it works (see Reviews), else goes home (see Repo screen).
- **While the agent works**, a line above the prompt moves, like Claude Code's: a star that grows and shrinks, a cat verb ("Prowling…", a new one every 20 s), how long it's been (`50s`, `1m 2s`), how many of its tasks are out in the background (`· 2 in the background`: the run sends a `background` entry whenever that changes, which the transcript doesn't show) and `esc to stop`. It sits outside the scrolling conversation, so it shows even when you've scrolled up, and goes away when the agent's done or waiting on you (a question, a proposal) or for its turn in the queue. The PR's mark in the list spins the same way. A turn that ends with agents still in the background isn't "done": only the run's last result is.
- **While Purr does what you asked for**, the same line says what it is, from the moment you press the key: `✻ Pushing… (2s)`, `Posting…`, `Approving…`, `Looking at its checks and reviews…` (`m`) or `Merging…`. A push, a post or a merge takes git or GitHub a few seconds, and nothing on screen changing reads as the key not working. Meanwhile the decision box gives way to it (all but the agent's question), the PR's mark in the list spins, and `a`, `x` and `m` do nothing on that PR (`SessionState.doing`; `PRKeys._doing`). There's no `esc to stop`: what's sent can't be taken back. Once it's done, the decision box says what's next.
- **What background agents are up to** shows in the PR's header, which stays put: Claude Code reports each one's progress (`task_progress`: its last tool and how many it's used), so the header reads `⟳ Reviewing · In the background: Bug scan · Grep · 14 tool uses`, the latest report winning. It's status, not the conversation: it isn't kept with the run's messages, and neither is the `background` count the working line uses.
- **Background tasks** (agents, long commands) get a line when they start and one when they end, named by what they are (`✓ background done: Bug scan`), not by what they reported: an agent's report is often a note to the main agent ("delivered to you as a message from …"). `◼ stopped` is neutral, since the agent stops what it no longer needs; only `✗ failed` is red.
- **How `c` works**: Purr suspends its UI and runs the real `claude --resume <session_id>` (your Claude Code, or the one the SDK comes with) in the PR's worktree, with GitHub writes disallowed via `--disallowedTools` (there, all of `gh api`). When you quit Claude Code, Purr comes back and picks the session up again. The PR's agent must be idle first, so two processes never drive one session. Because the transcript is the SDK's session file, what you did in Claude Code shows up in Purr's view afterwards.

## Commenting

`d` puts the PR's diff in the PR list's place (`tui/diffview.py`: `DiffPane`, which holds a `DiffView`), full screen, the most room for the code; `z` or `esc` shows the PR's conversation next to it, so you read the code and talk about it side by side (`z` again: full screen), and `d` closes it, zoomed or not, back to the list and the PR's pane (`esc` too, once it's not zoomed; from either pane), `shift+tab` goes to the PR's pane (`tab` opens and shuts things in the diff) and `tab` comes back. A cursor is on a line: `↑`/`↓` (or `j`/`k`, `ctrl+n`/`ctrl+p`: the diff takes those over from the app while it has the focus, `TAKES_OVER`), `page up`/`page down` (or `ctrl+v`/`alt+v`, as in Emacs), `home`/`end`. Each line shows its numbers in the base and in the PR. Lines added and removed have a faint green or red background across the row (the theme's success and error colors mixed into its background: `Palette.added`, `removed`), and the code is bright (the theme's bright text color, a list's titles', since the theme's own text color reads dimmed on the green and red), what its language marks (keywords, strings, numbers, built-ins, names being defined) in the theme's Pygments style's colors and comments dim; the style's own colors for plain names, operators and punctuation are left out, as they read dimmed (Solarized's operators are its comment color) (`tui/code.py`: the language from the file's name; each hunk highlighted a side at a time, as the code reads before and after, so a string or docstring over several lines is colored as one; the style's own background left out). A file in no language Pygments knows is plain. Files start as a line each, except in a short diff and those with comments on them: `tab` (or `space`, or a click) opens or shuts the one the cursor's in, `e` all. `n`/`p` go to the next or previous change: a file, or in an opened file, a hunk (its `@@` line, brought near the top, with what follows under it). (The diff is read once, in `purr/diff.py`: files, numbered lines, and the line and side a comment on each goes on.)
- **The lines around the changes.** What the diff leaves out (git's three lines of context aside) is a row each: a hunk's `@@` header for what's above it (`⋯ 397 lines (tab)  @@ -398,21 +398,30 @@ class LLMService`), and a row after the last hunk for the rest of the file (`purr/diff.py`: `gaps`, which numbers those lines in the PR and the base from the hunks around them). `tab` (or a click) shows them, all of them, and again hides them, as it opens and shuts files and comments: above a header, the header staying where it is on the screen with the lines nearest the change just above it (like GitHub's expand up); after the last hunk, below its row. They come from the file as it is in the PR (`GetFile` on the `git` worker: `git show <head>:<path>` in Purr's clone, a few ms; GitHub's contents API if the clone hasn't synced that head), read the first time, colored as the whole file. `enter` asks about them like any lines; `c` says why not: GitHub takes review comments only on the diff's lines.

- **Keys scroll smoothly.** A page, or the top or the end, glides there line by line in 0.15 s, however far, the way the wheel goes; a line or two moves at once, so a held arrow never lags. Another key on the way goes on from where the last was going, not from where its glide has got to. It's the same in the diff and the PR's conversation (`tui/scrolling.py`; Textual's own glides take a second to the top or the end, and a page goes at 50 lines a second).
- **The mouse.** The wheel scrolls a line at a time, everywhere (`PurrApp.scroll_sensitivity_y`; Textual's default is 2, which reads as jumpy). In the diff, the cursor comes along (onto the first or last line in view), so keys act where you look; a click puts the cursor on a line, `shift`+click selects up to it, and a click on a file's line opens or shuts it. Laying the rows out again (comments changed, threads read) keeps where you're looking rather than jumping to the cursor; the PR list, drawn again after a poll, keeps where you'd scrolled to as well.
- **Selecting and asking.** `shift+↑`/`shift+↓` select lines of code (over the comments between them), as in most editors; `ctrl+space` sets a mark that moving selects from, as in Emacs; `esc` (or `ctrl+g`) lets it go. `enter` asks the agent about the selection (or the line under the cursor): the PR's prompt starts with `About llm_service.py:415–416: `, and what you write goes to the agent with the lines, as they read in the diff, in a note ahead of it (`Quote`, `quote_note`: the transcript shows what you wrote). The answer is in the conversation, next to the code.


- **Your comments go to GitHub as you save them** (`enter` in the editor; `ctrl+j` a new line), as replies are: there's nothing of yours to post later. `c` writes one on the selection (several lines: GitHub's `start_line`, a multi-line comment), or on the line under the cursor (or someone's comment's): `PostLineComment`, a comment of its own at the PR's head, which then shows as yours in a thread. On the conversation (below), `c` writes on the PR itself (`PostPRComment`). Saving is your OK, as `a` is for the agent's review.
- **The conversation**, what's said on the PR itself rather than on lines (comments, and reviews' text with their verdict), is the view's first section, before the files, in the same boxes, opened when there's something in it; the PR's pane shows the latest five under the description. It comes with the PR's details (`PRDetails.conversation`, in the batched details query, so no request of its own), read again after you write there. `enter` on a comment of yours changes it (`EditPRComment`); on anyone else's (or a review's text, which can't be changed here), your comment on the PR, starting `@them`.
- **`r` on a comment on GitHub replies**, the editor starting with its words quoted (`> …`, as GitHub's quote reply does): in its thread for one on lines, on the PR for one in the conversation; posted when you save it. Elsewhere `r` is the repo's (review), and the footer says which.
- **Boxes** (`tui/boxes.py`): a comment's words rendered as Markdown, in a rounded border in its color with who wrote it and when on the top border, `@mentions` picked out; all the same width, as wide as the view leaves under the code (100 at most), laid out again when it's resized. Those on lines are under the code; the conversation's aren't indented. The PR's pane draws its conversation in the same boxes.
- **`x` on a comment**: yours on GitHub, deleted there once you've said so (`DeleteGitHubComment`: GitHub's own delete, on a line or on the PR; it can't be brought back); one the agent proposes, left out of its proposal (`DropProposedComment`); one of yours from before comments went as you saved them, dropped. Anyone else's stays.
- What's been said shows under its line, each in a box (its border and title in its color, on a tinted inside), which the cursor moves over as one: yours (yellow), the agent's proposed inline comments (magenta), so you see its review where it lands, and the PR's review threads on GitHub (cyan; `GetReviewThreads {pr}` on the GitHub worker, read in the background as the view opens, and their files open as they come). Each comment is a box of its own, with who wrote it and when on its top border (`╭─ ▾ alice · 3h ago · reply ─╮`; a thread's replies a little further in), which is all a shut box keeps (`╶─ ▸ alice · 3h ago ─ how it starts… ─╴`); `@mentions` are picked out. `enter` on a box opens the editor with its words: on the agent's, to rewrite its proposed comment (`EditProposedComment`: approving posts your words); on one of yours on GitHub, to change it there when you save it (`EditGitHubComment`); on anyone else's, for your reply in its thread, posted there when you save it (`ReplyToThread`). `tab` (or a click) on a comment shuts it to its top line and opens it again; resolved threads start shut. One on a line no longer in the diff (outdated) goes at the end of its file. The side GitHub puts it on (`diffSide`) places one on a deleted line.
- Comments used to be drafts until you posted your review (the `draft_comments` table). Any still there from then go out as before: with the agent's proposal when you approve it, or on their own (`Post your 2 comments? [a]`).
- GitHub places a comment by line and side: a line the PR adds or keeps is on the `RIGHT` (its number in the PR), a deleted one on the `LEFT` (its number in the base). The diff view knows which from the diff, so a comment on a deleted line lands on it. Comments written on an earlier commit (the PR moved on since) go in a review of their own on that commit, where GitHub shows them as outdated, rather than on the wrong line.
- Jobs, on the GitHub worker: `PostLineComment {pr, path, line, side, body, head_sha, start_line?, start_side?}`, `PostPRComment {pr, body}`, `EditPRComment {pr, comment_id, body}`, `DeleteGitHubComment {pr, comment_id, on_line}`, `DropProposedComment {pr, index}`; for drafts from before, `SaveComment`, `RemoveComment` and `PostComments {pr}`. A `comments.changed` event refreshes the PR's pane.

## Merging: your final decision

Approving and merging are apart on purpose: two people may be reviewing a PR (two assignees), and you may want the other one to approve as well. Once you've approved a PR, through Purr or on GitHub, its pane says so (`You approved it. [m] merge…`).

- **The first `m`** reads where the PR stands, fresh from GitHub (`CheckMerge`, one GraphQL request): each check on its head (GitHub Actions runs and statuses like readthedocs; passed, failed or still running, and whether the base branch's rules require it), the head's workflows (`checkSuites`: those GitHub holds for approval, and those starting, which have no check run yet), the assignees' latest reviews, and GitHub's own merge state. `purr.merging` splits that into:
  - **blockers**, which stop it outright: you haven't approved it (your latest verdict, through Purr or on GitHub, isn't an approval), it has commits since you did (approve again: you'd be merging what you haven't reviewed), it has conflicts, it's a draft;
  - **concerns**, which are your call: a check that failed (a docs build failing needn't hold up a fix), one still running, workflows that haven't run because GitHub waits for someone to approve them, an assignee who hasn't approved (or requested changes), a branch rule GitHub says isn't met (it may refuse, and says why), GitHub still working out whether it can be merged.
- The pane shows it: `Squash and merge #6902 into main?`, how many checks passed, then each concern. **`m` again merges anyway** (`MergePR`), with your default merge method in the repo (what GitHub's own page picks for you: merge, squash or rebase), and only at the commit you approved: GitHub refuses if the PR moved on meanwhile.
- It's checked again just before merging. If something new came up since you looked (a check that was running failed), it doesn't merge; the pane shows how it stands now, and `m` again decides on that. Things that only got better (the check passed) don't count. `x` closes the box: `m` asks GitHub again next time. Moving to another PR or repo, or home, keeps it: it's there when you come back, up to date.
- When something blocks it, the pane says what (`Can't merge #6757 yet: ✗ It has new commits since you approved it`), and `m` checks again; if nothing changed, it says so (`Still can't merge: …`). `x` closes it. It also goes once it's moot, and `m` asks again: when you write to the agent (to fix what's in the way, say), when the agent proposes something (the push of that fix), and when the PR has new commits (`SessionState.head`). Otherwise it would stay above what's next, since it comes before proposals in the box. If GitHub has commits Purr hasn't seen yet, Purr polls right away, so they bring the PR back for review.
- **While CI runs**, the box lists every check, as GitHub's page does, in GitHub's order: a spinner on each one still running, with how long it's been at it (`⠹ Unit Tests (required)  1m 12s`), and a mark on the rest with how long they took (`✓ Build  18s`, `✗ Docs`); the times come from each check run's `startedAt` and `completedAt` (a status, like readthedocs, has only when it said it was pending). Past 12 checks, those that passed are one line (`✓ 14 more passed`). Listed checks aren't repeated as concerns. Once none is running, the box is back to a line for those that passed (`_check_lines` in `tui/merge_box.py`). The spinners turn on a timer while the box shows checks running (`PRSession._spinning`), and the box stays current: Purr asks GitHub again every 5 seconds (`MERGE_RECHECK`) until none is, so a check that finishes or fails shows as it happens, without pressing anything. This goes on in the background when you move to another PR, another repo or home (one at a time per PR: `PRKeys._follow_merge`, an app worker), and the PR's mark in the list spins meanwhile. If it ends while you're elsewhere, only that mark changes. It stops when GitHub is done, when you merge or close the box, when the PR gets new commits, or when the PR's gone (closed, say): then the box goes, and `m` asks again. If GitHub can't answer just then, it's asked again next time.
- **While GitHub works out whether it can be merged** (right after a push, or when its base moved on, GitHub says `UNKNOWN` until it has checked for conflicts, which takes seconds once asked), the box lists the checks the same way, with a spinner below them in place of the concern (`⠹ GitHub is working out whether it can be merged`), and asks GitHub again every 2 seconds (`MERGEABLE_RECHECK`) until it knows. Then the box says what it found: nothing more if it can be merged, or that it has conflicts. Merging meanwhile is your call (`[m] merge anyway`). The box waits on GitHub this way, for either reason, only while nothing blocks the merge (`settling` in `tui/merge_box.py`).
- **When CI hasn't run** because GitHub holds the workflows for approval (a PR from a fork, by a first-time contributor), the box says so instead of letting one passed check look like CI passed (`⚠ CI hasn't run: 4 workflows wait for approval (build, tests, format, coverage)`), and offers **`a` to approve and run them** (`[a] approve and run CI`), like GitHub's *Approve and run workflows* button: each run is approved (`ApproveRuns`, `POST /repos/{repo}/actions/runs/{id}/approve`; GitHub only lets you if you can write to the repo, and says so otherwise), and the box follows them as they run, as above. A workflow that's starting shows as running from the start, with its workflow's name, until GitHub lists its jobs. Only GitHub Actions suites count: other apps' suites can stay queued forever with nothing to run.
- The PR shows merged at once (and its worktree goes); the next poll would only find it out. The commit an approval was of is kept when it's posted (`pending_actions.posted_head`).
- **Then on to what's next.** Merged, the PR's done with, and so is one you requested changes on (`a`, its author's turn now): the cursor goes on to the first PR to merge, else to the first that needs you, as listed (`RepoView.next_for_you`), and the note says so (`Merged #6779 into main · next: #6801, to merge`). Only if you're still on it: merging takes seconds, and if you moved on meanwhile, the cursor stays where you put it. Approving doesn't: the PR goes to To merge, and the cursor with it, since merging it is next.

## Pushing: what the agent changed

When you ask the agent to change a PR (a fix, a test), it edits the PR's worktree. It can't push (`git push` stays denied, see Permissions), but you can have Purr push what it committed:

- Ask for it ("push it"). The agent commits on top of the PR's head and proposes a push (`propose_action` with kind `push`), only when you ask for one. If it tries `git push` anyway, the refusal tells it to propose one instead.
- Or ask it to rebase the PR (or squash or reword its commits). The push then replaces the branch's commits: `Force-push 3 commits, up to e0b9581, to eric7h:fix/units, replacing its 2 commits?`. The commits listed are the branch's as they'd be, from where it leaves the branch it merges into, which Purr fetches first (the agent likely rebased on its latest, and main's own commits aren't the PR's); `payload.replaces` is how many it had.
- Purr works out what would go where and names it, whatever the agent said: `Push e0b9581 to eric7h:fix/units-temperature-degrees?` (or `Push 2 commits, up to e0b9581, to …`), with each commit's subject under it. A merge of main into the PR is one commit there: what it brings from main is main's already, so it isn't listed (`git log --first-parent`). It refuses, telling the agent why, when nothing's committed, changes are left uncommitted, a rebase is halfway, GitHub has commits Purr hasn't seen yet, the PR's branch is gone, or its author doesn't allow edits by maintainers on their fork (your own fork is fine).
- `a` pushes them as you, from Purr's clone, to the PR's branch in its repo: a fork's URL is the clone's (https or ssh) with the fork's name. The push carries a lease on the head the commits were made on (`--force-with-lease`), so a push that came in meanwhile is never overwritten (the same lease lets a rebase replace the branch); if GitHub refuses, the proposal is back, to try again or dismiss. `x` dismisses it.
- A push isn't a verdict: the PR still needs you (`No verdict yet`, `[a] approve PR`). What you pushed is its head right away (`Store.pushed`), so an approval next is of what you pushed, not of the commit before. Its review has seen those commits too (`reviews.head_sha`): they were made in its session, with your OK, so the next poll doesn't take them for new commits to re-review. Neither does a poll whose search still has the head from before the push (see Polling).
- **The diff shows what the agent committed** before you push it, so you can read the change first. While the PR's worktree has commits on top of the PR's head (or the PR rebased there), `d` shows the PR as it'll be once they're pushed, and its title says so (`Diff #6756 · with 2 commits not pushed yet`, or `· rebased, not pushed yet`). It's the worktree's head diffed against where it leaves the base (`GitRepos.local`, `local_diff`); after a rebase or a merge, the base is fetched first, or main's newer commits would show as the PR's. A worktree on an older head (the PR moved on since) doesn't count. The diff is fetched again whenever the agent's turn on the PR ends and when a push settles, and an open one is redrawn in place: the same files open, the cursor on the file it was in (`DiffPane.update`). What's said on lines of the PR as on GitHub (threads, your comments, the agent's) moves with those lines (`diff.mover`, from a diff with no context of the commits); on a line they changed, it's outdated. `c` doesn't comment on lines then, since GitHub takes comments only on lines it has: push first, or ask the agent about them (`enter`). Comments on the PR itself, replies and edits work as usual.

## Permissions: Claude Code's own

Reviews use Claude Code's permission system, not one of Purr's own (`review/agent.py`, `review/rules.py`):

- **Claude Code's auto mode** (`permission_mode`, `--permission-mode`): safe things run, and Claude Code asks before anything it judges risky. Your Claude Code settings (`~/.claude/settings.json`) and their rules apply, as everywhere else.
- **When Claude Code asks**, the question goes to Purr (`can_use_tool`): the PR moves to *Needs you* and the prompt shows in its pane. `a` allows once, `x` denies, `A` keeps Claude Code's own suggested rule (`Bash(uv run pytest:*)`): *everywhere* goes into your Claude Code settings (so it applies in Claude Code itself too); *this repo* goes into Purr's Claude Code settings for the repo (`~/.config/purr/repos/<owner>/<name>/settings.json`), which that repo's reviews load. `i` then `p` opens them (at home, your Claude Code settings).
- **Purr's one rule:** nothing that changes GitHub (reviews, comments, merges, `gh api` writes, `git push`) and no reading your GitHub token. As Claude Code deny rules, plus a check before every tool call (`review/policy.py`) for forms the rules can't see (`bash -c 'gh pr merge 12'`). The agent proposes; Purr posts what you approve.
- **The sandbox, optionally** (`--sandbox`): Claude Code's own, where the operating system confines the agents' commands to the PR's worktree and a few domains (GitHub, PyPI, npm), and they run without asking. Off by default: on Ubuntu 24.04 and later, AppArmor's `bwrap-userns-restrict` profile stops it (Claude Code's sandbox nests a second user namespace, which that profile refuses), so it only works once that's allowed.
- Why not Purr's own rules: an earlier version parsed commands to guess what was harmful. Shell is too flexible for that to be reliable, it asked about plenty of harmless things (`sed -n`, `cd`, `git -C`), and Claude Code already does this, better, with your rules.

## What the agent knows

Each PR's chat is Claude Code: the Agent SDK with Claude Code's own system prompt (`claude_code` preset) and built-in tools, plus what it needs for reviewing, in this order:

1. **Purr's review instructions**: how to review, the `submit_review` / `propose_action` / `get_review_threads` tools, read linked issues, never touch GitHub.
2. **The repo's own guidelines**: its `CLAUDE.md` and `AGENTS.md` (with `@file` imports resolved, as Claude Code does), read from the default branch rather than the PR, so a PR can't rewrite the rules it's reviewed against. For pipecat that's AGENTS.md: docstrings, deprecations, writing for future readers.
3. **The repo's review skill**, when its reviews follow one: how to fit it into Purr (see Review workers).
4. **The lead's plan**: "How this review should go" (depth, priority, focus).
5. **Your instructions**, which take precedence: plain Markdown files, like a CLAUDE.md, each for all repos and optionally per repo:
   - **Review style** (`review.md`): how reviews should go (tone, what to raise, what to skip).
   - **Code style** (`code.md`): what good code looks like to you, which reviews hold the PR to. Yours starts with: prefer a generic solution over special cases, avoid piling up flags to keep state, keep functions short.

   They live in `~/.config/purr/` (`review.md`, `code.md`) and `~/.config/purr/repos/<owner>/<name>/` for one repo. `i` asks which one to edit (`r` review style, `c` code style) and opens it in Purr's editor: the repo's inside a repo, the general one at home. `p` there opens your standing permissions, and inside a repo, `s` chooses which of its skills reviews follow. New files start with a short how-to in an HTML comment that isn't sent to the agent. Everything here is sent with every turn, so edits apply to sessions already under way.

The repo's own skills and agents aren't prompt text: they're loaded as a plugin, from the default branch (see Review workers), e.g. pipecat's `docstring` and `changelog` skills and its `code-review` workflow. Skills that are only for people (`disable-model-invocation`, like `code-review`) aren't offered to the agent, but a review can start with one: the repo's review skill, or any skill you type as a slash command.

Where it differs from Claude Code on purpose: nothing from the PR's own `.claude/` is loaded, since the PR could tamper with it. Skills and agents come from the default branch instead, and the repo's `settings.json` (hooks) isn't used at all. Tool permissions are Claude Code's own, plus Purr's one rule (see Permissions).

## The activity log

Every Purr event that's worth keeping (`recorded`) is appended to an `activity` table: PRs entering the pool or getting assigned to you, review requests and replies, new commits on PRs under review, PRs closed or merged, reviews started, finished or failed, actions proposed or resolved, agents blocked on a permission prompt. Progress, streamed session messages and list refreshes aren't. It doubles as each PR's timeline, and it's where the news comes from after a restart (see Alerts from other repos): while Purr was closed nothing ran, but the first poll after startup records what changed on GitHub in the meantime, so that's news too.

## Bus messages

Jobs are requests one worker answers, within a timeout (60 s; 180 s for `PlanReviews`, 120 s for `GetWorktree`). Each is a dataclass in `src/purr/messages.py` that names the worker that handles it and its reply, also a dataclass: `class SendMessage(Request[MessageSent])`. The plumbing is in `src/purr/jobs.py`, once: a worker handles one with a method decorated `@handles(SendMessage)` that takes the request and returns the reply, and any worker (the TUI, the lead, a test) sends one with `request(sender, SendMessage(pr=..., text=...))`, which returns the reply. On the bus they're JSON (pydantic encodes the dataclasses), so they could cross a network bus later. A request that can't be done raises a `PurrError`, which goes back as itself (class and message), so a caller can tell `Busy` from `NotFound` from `Invalid`, `Failed` or `Unanswered` (no answer in time) without reading the text; anything else a handler raises is logged and goes back as a plain `PurrError`, so the asker hears about it at once rather than timing out.

Jobs:
- `PlanReviews {prs, depth}` (lead worker): plan and start reviews you asked for (TUI `r`; later, voice); answers once they've started, with why any didn't.
- `StartReview {pr, plan}` (reviews worker, sent by the lead; without a plan, a full review)
- `Rereview {pr, plan}` (reviews worker, sent by the lead on new commits)
- `SkipUpNext {pr}` (upnext worker): the PR isn't for you; it leaves Up next for good (`s`).
- `SendMessage {pr, text}` (reviews worker): say something in a PR's conversation. Its reply says what that did besides: answered a permission request (a no, with directions), set proposals aside, or went to the agent at work.
- `AnswerPermission {request_id, allow, remember}` (reviews worker): answers an agent's permission request; `remember` (`repo` or `all`) also keeps its rule as a standing permission.
- `SetModel {pr, model}` (reviews worker): the model for a PR's conversation (`/model`).
- `ListRepoSkills {repo}` / `ListReviewSkills {repo}` (reviews worker): a repo's skills, for `/help` and completion; those that may be for reviewing, and which one its reviews follow.
- `ChooseReviewSkill {repo, skill}` (reviews worker): have its reviews follow `skill` ('' for Purr's own; none: ask again next run). Answers a `review.skill_question` too.
- `SuggestPrompt {pr}` (suggestions worker): what you might ask next in the PR's session, from the end of its conversation (see PR session).
- `WatchRepo {repo}` / `UnwatchRepo {repo}` (GitHub worker; `repo` can be `owner/name` or a GitHub URL)
- `AssignMe {pr}` (GitHub worker): assigns you, when `r` starts a review of a PR that isn't yours yet (one in the pool, one asking for your review, or, once you confirm, one someone else has).
- `MarkSeen {pr}` (GitHub worker): you looked at a PR that had news; stores when, so it isn't news after a restart.
- `FetchDetails {prs}` (GitHub worker): description, base and head branches, +/- lines, files, labels, review decision and CI state of some PRs, batched 20 to a request.
- `GetDiff {pr}` (git worker): the PR's unified diff, from Purr's clone, or from GitHub if the clone doesn't have the PR's head yet; with what the agent committed in the PR's worktree that isn't pushed yet (see Pushing).
- `GetWorktree {pr}` (git worker): the PR's worktree, made again if it was removed (for `c` and `!`).
- `DismissReplies {pr}` (GitHub worker): the PR's replies to you need no answer (`x`).
- `CheckMerge {pr}` / `MergePR {pr, seen}` (GitHub worker): where a PR stands for merging, and merging it past the concerns you saw (see Merging).
- `ApproveAction {action_id}` / `DismissAction {action_id}` (GitHub worker). Approving claims the action atomically (so two requests at once can't post it twice), posts the GitHub review with its inline comments and yours (see Commenting), and marks the PR Done if it was a verdict (approve, request changes) and nothing else is pending; after a comment it still needs you. If GitHub won't place an inline comment (line outside the diff), the comments go into the review body. If posting fails, the action goes back to pending for a retry. An approval with nothing to say is "LGTM". The proposal in the PR's conversation shows it too, so `a` posts exactly what you read. A push proposal is pushed instead (see Pushing). `ApprovePR {pr}` approves a PR with nothing proposed (it waits for your verdict alone), as approving an approval proposal would: LGTM, at its head.

Events (broadcast, everyone listens):
- `pr.list_updated` (repos, PRs or their states changed; re-read the store)
- `github.synced` (a poll finished: what the store says about GitHub is current)
- `git.synced` (the clones have every open PR the store has: their sizes and diffs are local)
- `pr.changed {pr, change, title, by}` (from the poller: assigned, unassigned, pooled, unpooled, new_commits, closed, merged, requested, replied; `by` says who replied)
- `review.started {pr, plan}`
- `review.progress {pr, text, waiting}`
- `review.finished {pr, summary, findings}`
- `action.pending {pr, action_id, description}`
- `action.resolved {pr, action_id, approved}`
- `review.failed {pr, error}`
- `session.message {pr, message}` (one streamed SDK message: text, tool call or tool result)
- `session.permission_request {pr, request_id, tool, description, reason, rule}` / `session.permission_resolved {pr, request_id, allowed, answered, description}`
- `review.skill_question {repo, skills}` (a repo's reviews wait to hear which of its skills to follow) / `review.skill_chosen {repo, skill, chosen_by}`

Events (`PurrEvent`) are `BusDataMessage` subclasses in `src/purr/messages.py`, broadcast (no target), with plain JSON fields (PRs as `owner/repo#123` strings), since everything that listens gets them, and most go into the activity log. Every event is also logged as one line, its values cut to 200 characters: a `session.message` carries whole tool results, which the session's transcript already keeps.

## SQLite store

- `repos`: name (`owner/name`), added_at, synced_at (first complete poll; until then its pool isn't reported as new). The watched repos, managed from the UI.
- `prs`: repo, number, title, author, author_association, url, head sha, base, state (Purr's: not_reviewed/reviewing/needs_you/done) and state_at (when it got there), gh_state (open/closed/merged), assigned_to_me, assignees, requested_from_me, involved (you took part on GitHub; it sticks), replies (to you, since your last word, JSON) and replies_done_at (`x`), created_at, updated_at, model (yours, from `/model`), seen_at (when you last looked at it; what happened before isn't news). Descriptions and files aren't stored; the UI caches them in memory.
- `reviews`: pr, session_id, worktree path, status, summary, error, head_sha (the commit it last looked at), skill (the repo skill it followed), plan (the lead's, JSON), started_at, finished_at
- `findings`: review, file, line, severity, text
- `draft_comments`: id, pr, path, line, side (`LEFT`/`RIGHT`), body, head_sha, created_at. Your inline comments until they're posted (see Commenting).
- `pending_actions`: id, pr, kind (comment/request_changes/approve; the schema also allows merge, which nothing proposes), description, payload, status (pending/approved/dismissed/executed/failed), created_at, resolved_at, posted_head (the PR's head when it was posted)
- `review_skills`: repo, skill ('' for Purr's own review), chosen_by (`purr` or `you`), chosen_at
- `up_next`: repo, number, rank, why, by (`lead`, or `purr` when the lead couldn't say), picked_at. What's up next in each repo (see Up next).
- `up_next_skipped`: repo, number, title, author, skipped_at. The PRs you said weren't for you (`s`).
- `prompts`: at, repo, number, text. What you asked PR agents, for the prompt's history (`↑`/`↓`, `ctrl+r`).
- `activity`: at, pr (optional), kind, data. Every recorded Purr event; the news after a restart, and each PR's timeline.

- `runs`: one per time an agent works on a PR: kind (`review`, `resume`, `rereview`, or `message` for one of yours), repo, number, review and session ids, queued_at / started_at / finished_at (UTC, ms; queued to started is time waiting for a slot), status (`queued`, `running`, `finished`, `failed`, `interrupted` by a shutdown), error, and what the SDK reports at the end: model, cost_usd, turns, duration_ms, api_duration_ms, input/output/cache read/cache write tokens.
- `messages`: every message of every run, in order: at (UTC, ms), run, repo, number, kind (`prompt`, `thinking`, `text`, `tool_use`, `tool_result`, `task` (a background agent or command starting or ending), `permission_request`, `permission_answer`, `result`, `error`), author (`purr`, `you`, `agent`, `tool`) and the message itself as JSON (tool results are capped at 2,000 characters, as in the transcript).

Both are written as things happen, so they're there for analysis even if a worktree or Claude Code's session files go. They're kept by repo and number, like `activity`, so they outlive the PR's row. Sessions continued in Claude Code itself (`c`) aren't recorded, and conversations from before these tables aren't either (Claude Code's session files have them, with timestamps, to import if needed). For example, with `sqlite3 ~/.local/share/purr/purr.db`:

```sql
-- What reviews cost and how long they took, by repo
SELECT repo, count(*), round(sum(cost_usd), 2), round(avg(duration_ms) / 1000) AS avg_s
FROM runs WHERE kind = 'review' AND status = 'finished' GROUP BY repo;

-- Which tools the agent reaches for
SELECT json_extract(data, '$.name') AS tool, count(*) FROM messages
WHERE kind = 'tool_use' GROUP BY tool ORDER BY 2 DESC;

-- How long permission requests waited for you
SELECT q.repo, q.number, (julianday(a.at) - julianday(q.at)) * 86400 AS waited_s
FROM messages q JOIN messages a ON a.run_id = q.run_id AND a.kind = 'permission_answer' AND a.id > q.id
WHERE q.kind = 'permission_request' GROUP BY q.id;
```

- **Header**: where you are (`Purr › 2 pipecat-ai/pipecat`) and the latest alert from other repos.
- **Left pane**: the repo's PRs grouped (Needs you, To merge, Reviewing, Review requested, Up next, Waiting on author, Done, Others reviewing, Not reviewed), newest first within each group (Done: latest done first). Columns: number (in its own color), title (bright, as under the cursor; bold when there's news), who's assigned (`you`, a login, `+1` for more), author, and how long ago it was opened (`2h`, `3d`, `5mo`), a space off the right edge. A thin dim line goes between PRs; each group's heading is its name and count followed by a double line in its color to the edge (`▾ ⚠ NEEDS YOU (1) ════`), two blank lines after the group before it. The cursor stops on headings, as on the files in the diff: `tab` (or `enter`, or a click) on one folds its group to that line (`▸`) and opens it again, for as long as Purr runs. While searching, every match shows, folded or not; going to a PR in a folded group (an alert, `ctrl+p`) opens it. Home's two groups (watched, not watched) have the same headings, without folding (`tui/lists.py`).
- **Right pane**: the selected PR, top to bottom:
  - **Header**, which stays put: its title, then `by alice · opened 3d ago · main ← fix-bus · +22 −4 · ✓ checks pass · approved · labels`, then where its review stands. Too long for the pane, that line wraps between its parts, never through one: where the PR stands (`✓ checks pass · approved`) goes to the next line whole (`Parts` in `tui/overview.py`, laid out at whatever width it's drawn). CI says `⏸ CI needs approval` while GitHub holds workflows for approval, whatever else passed, and `⟳ checks running` while a workflow is starting (`_ci` in `github.py`).
  - **What scrolls**: the PR's description, then where it changes things, then the session with the agent (Claude Code style, see PR session). A PR nobody has reviewed yet opens at its description, so you can decide whether to take it; a reviewed one opens at the end of the conversation.
  - **The working line, the decision box and the prompt**, which stay put too. The decision box asks what waits on you, the most pressing first (`_QUESTIONS` in `tui/session.py`, one function each): a permission request (`a`/`A`/`x`), where it stands for merging after `m`, a proposal (`a`/`x`), replies to you (`x`), then, once you've approved it, `[m] merge…`. It shows only when it's needed (`_decision`). The agent's question always shows: the agent can't go on until you answer, and what you type may be the answer (`or write what to do instead`). The rest hide while you type, since `a` and `x` type letters there and sending sets a proposal aside; deleting what you wrote, or `esc` out of the prompt, brings them back. They also hide while the agent works on the PR (a review, or what you wrote), since what it says next may change them, and `a` and `x` do nothing on it meanwhile; where the PR stands for merging still shows then, since you asked for it with `m`. Sending marks the agent at work at once (`PRSession._on_its_way`), so the box doesn't flash back before the agent reports what it's doing. The prompt takes several lines and grows with them (up to 10).
  - **Not the diff**: the pane is for deciding whether to take a PR and talking with the agent, and the agent reads every file anyway. So after the description it says where the change is in a line (`17 files changed: most in rtvi (8), evals (5)`: its files if there are three or fewer, else the folders with most lines changed, from the file list GitHub sends with the details, the first 100), and the header says how big (`+412 −388 in 17 files`). The diff itself is `d`'s, a keypress away and with the comments on it.
  - `d` opens the diff view (see Commenting); `D`, the whole diff in your pager (`gh pr diff`).
- **Details are fetched ahead; diffs are local.** Selecting a PR fetches its details from GitHub (about 0.5 s), plus those of the 10 PRs below it in one request, and its diff, so `d` opens at once: from Purr's clone (`GetDiff` on the `git` worker, see Repos), in a few ms. Details are cached in memory and refetched when the PR is updated or after 2 minutes, since CI moves on without the PR changing; diffs are kept by head commit (the last 50), and dropped when the agent's turn on the PR ends (it may have committed).
- **Focus**: each pane has a rounded border, and the one with the focus lights up in the accent color, with its title (`PRs`, `PR`). `tab` goes back and forth between them; `enter` on a PR goes to its prompt.
- **Status bar**: key hints for the focused pane.
- **Selecting text**: drag over the PR pane (its description and the conversation) and it's copied, as in a terminal; `ctrl+c` copies it too (Textual's binding). Textual's `RichLog` can't be selected in, so the pane is a `Transcript`, a `RichLog` that marks where each line's text is. Copying asks the terminal (OSC 52, which works over ssh) and also runs the system's copy command if there's one (`wl-copy`, `xclip`, `xsel`, `pbcopy`): GNOME Terminal and the other VTE terminals ignore OSC 52, so there it takes `wl-clipboard` or `xclip`, and Purr says so. `shift`+drag selects with the terminal itself, anywhere.
- **Colors**: a Textual theme, the `theme` setting: Solarized dark unless you choose another of Textual's (`nord`, `gruvbox`, `dracula`, `tokyo-night`, `catppuccin-mocha`, `solarized-light`, `catppuccin-latte`, ...; a wrong one lists them). The theme does the widgets. Rich's named colors in Purr's text (`green`, `red`, ...) map to Solarized's terminal palette under its two themes, to Textual's own under the others. The few colors Purr picks itself (`Palette` in `tui/theme.py`: list rows' titles, PR numbers, the comment boxes' inside, the working line, the code style, the diff's green and red) are Solarized's under those two, and the theme's otherwise (its text a little brighter, its primary color, its panel, its warning color, its background tinted with its success and error colors); code in descriptions and replies uses the theme's Pygments style where there's one (`nord`, `dracula`, `gruvbox-dark`, ...), else `github-dark` (`default` in a light theme). It changes while Purr runs too, from the theme picker (`i` then `t`, or `/theme`) or by saving `settings.toml` with another `theme` in it (`i` then `o`): the widgets and the named colors take it at once, and what Purr drew in its own colors is drawn again (`PurrApp.change_theme`: the lists, the PR's pane, the diff).

### Alerts from other repos

News is something you'd want to know that happened since you last looked at a PR: it was assigned to you, someone asked for your review, its review finished or failed, its agent needs your OK, or someone replied to you. Review progress doesn't count. What's news, and how it reads, is in `purr/news.py`, the same for live alerts and after a restart.

- **The top bar says one short thing about other repos**, on every screen, so you know to go and look: the latest news there if there's any (`🔔 2 · whisker#112 review: found 2 issues  (ctrl+n)`), otherwise how many PRs need you there (`⚠ 3 need you in other repos  (0)`). `0` goes to the repo list, which says where: a ● after each repo with news, and its NEEDS YOU count.
- **In a repo, PRs with news have their title in bold**, like unread mail, until you look at them. News about the PR you're looking at isn't news.
- `ctrl+n` jumps to the newest news in another repo (or in this one if there's none elsewhere); pressing it again goes through the rest.
- **It survives restarts.** Looking at a PR stores when (`prs.seen_at`, through a `MarkSeen` job), and on startup the news comes from the activity log: what happened to open PRs since you last looked at them.

### Moving around

Global keys work everywhere, even while typing in a PR prompt:
- `ctrl+p` quick switcher: fuzzy search over repos and PRs (number, title, author); with nothing typed, the PRs that need you, then the repos. Built on Textual's command palette.
- `ctrl+o` back to where you were before the last jump (repo and PR); press it again to return, like `cd -`.
- `ctrl+n` jump to the newest alert from another repo.
- `q` / `ctrl+q` quit (it asks first, saying how many reviews are running; they resume next time). `ctrl+c` doesn't quit.
- (Planned) a push-to-talk key (hold) for voice.

List and pane keys (letters and numbers act on lists and panes; while a prompt has focus, typing goes to the agent, as in Claude Code):
- `0` repo list, `1`–`9` repo by number
- `+` add a repo, `-` remove one (repo list)
- `enter` opens a repo; on a PR, it goes to its prompt.
- `o` opens the PR on GitHub, in your browser (at home, the repo), from either pane (`tui/browser.py`: the system's opener, `open` or `xdg-open`, its output thrown away so a browser starting up doesn't write over the screen).
- `tab` (or `shift+tab`) switches between the PR list and the PR's pane, from its prompt too (the prompt never takes a tab). On a group's heading in the list, `tab` folds or opens the group instead (the footer says which: `Fold/open` there, `PR` on a PR), and `shift+tab` still switches.
- `?` on any page lists every key that works there (`tui/keyhelp.py`): made from the active bindings, grouped from the focused pane outwards (the pane, the repo, everywhere), so it can't drift; each page's footer shows `? Keys` first.
- The footer (`tui/keybar.py`, Purr's own: Textual's is one line, which a pane's keys outgrow) shows every key that works where you are, on as many lines as that takes (two at 140 columns), never breaking a key across lines, a ` │ ` between keys: the focused pane's first, in the order it binds them, then the repo's, each key once (the nearest binding of it); those that work everywhere (`ctrl+p`, `ctrl+n`, `i`, `0`, `1–9`, `q`) are left to `?`, and so are the decision box's (`a`, `A`, `x`, `m`), which the box itself says, with what each does (`show=False` in `tui/keys.py`). Keys in a group go together (`n p Next/prev`). What it shows changes with where you are: in the prompt, `enter` sends, `ctrl+j`, `↑` history, `ctrl+r` and `esc` (the letter keys are for typing there); in the search box, `enter` and `esc`; on a group's heading, `tab Fold/open`; in the diff, `⇧↑ ⇧↓` select, and `esc` unselects while there's a selection (`d` closes then). Every key works from either pane, since they're about the PR (selected in the list, shown in the pane): `RepoView` binds them all, and each pane binds the ones it shows first, running the repo view's action. One table says which (`tui/keys.py`). `?` lists them grouped, with the ones the footer leaves out (moving, paging, the Emacs keys).
- `n` / `p` next / previous: repo, or PR, over the groups' headings (the arrows stop on them). Moving stops at either end of the list rather than wrapping round, and at a group's first PR its heading shows too. They only change which PR the PR's pane shows, never the focus, so from the pane you read PRs one after another.
- `/` search the PR list as you type (number, title, author, assignees; every word has to match), in a box above the list. `enter` (or `esc`) goes back to the list, keeping the results. The search stays (shown above the list, per repo, also after leaving it) until `esc` clears it (from the list or the PR's pane: every PR again, the cursor on the one it was on; the footer says `esc Clear search` meanwhile), or you press `/` and delete it.
- `esc` goes a step back at a time: zoomed (the PR's pane or the diff), it zooms out, the focus where it was; in the PR's pane, it stops the agent at work (see Reviews). Then it goes home from the list or the PR's pane, once there's no search. From the search box it goes back to the list (the search stays); with a search on, it clears it; from the prompt it goes back to the PR's pane (the `/` suggestions close first), even while the agent works: a further `esc` stops it, or goes home. Anything half-typed in the prompt is there when you're back.
- `page up` / `page down` scroll a page (smoothly), in either pane (the transcript while typing too); reading the PR's pane, `ctrl+v` / `alt+v` (meta+v) too, as in Emacs (typing, `ctrl+v` pastes)
- `space` mark/unmark PR; `esc` (or `ctrl+g`) unmarks them all, before it does anything else (the footer says `esc Unmark` meanwhile)
- `r` start review on marked PRs (or the selected one), assigning you; on one already reviewed, it asks first
- `s` on an Up next PR: not for you (see Up next)
- `d` the diff view, to read it line by line and comment (`D`: the whole diff in your pager)
- `a` / `x` answer the decision box: do or dismiss a pending action, allow or deny a permission request (`A`: always allow); `x` also says replies to you need no answer. The decision box says what each does (`[a] request changes   [x] dismiss`), so the footer doesn't show them. `?` names what `a` does now, so it never surprises: *Post comment*, *Approve PR*, *Request changes* or *Push* for a proposal, *Allow once* for a question, *Post comments* for yours on their own, *Approve PR* for a PR waiting for your verdict alone (`SessionState.a_does`; `?` asks the screen, `MainScreen.describe_key`). With nothing for it to do, `a` does nothing, and `?` doesn't list it
- `m` merge a PR you approved: once to see where it stands, again to merge (see Merging)
- `t` the agent's reasoning in full, or a line per thought again
- `z` zoom the PR session to full screen, and back, the focus where it was (the PR's pane, or the list). The transcript is written again to fill its new width (a RichLog wraps each line once, as it's written; `Transcript.Rewrap`), as when the terminal's resized
- `c` open the PR's session in Claude Code, `!` a shell in its worktree
- `i` the settings (`SettingsScreen`): in two sections, how reviews go (*Reviews, in every repo*, or *in owner/repo* inside one: review style `r`, code style `c`, the agents' permissions `p`, the repo's review skill `s`) and *Purr* (its settings `o`, its theme `t`: Textual's themes in a list, each shown as you move to it, Purr's own colors too; `enter` keeps it in `settings.toml`, `esc` goes back to the one you had). Each entry says what it's for and where it is (its file, or the theme in use); the arrows and `enter`, or its letter, open it over the menu, and closing that comes back to the menu, drawn again. Files open in Purr's editor (`tui/editor.py`), full screen, with the prompt's keys (Emacs's, and Textual's: shift to select, `ctrl+x`/`c`/`v`, `ctrl+z`; `tui/editing.py`), `ctrl+s` to save and `esc` to close (asking first, with changes not saved); what Purr reads (`settings.toml`, the JSON permissions) is checked before it's saved, the reason shown under it if not

### Fast by default

- Nothing on screen waits on the network or an agent. Every screen draws from local state, so switching repos or PRs takes effect on the next frame (target: well under 50 ms).
- Lists are re-read from SQLite (milliseconds) when bus events say something changed, a burst coalesced into one redraw (50 ms). What comes from elsewhere is cached in memory: PR details, diffs, and transcripts.
- Startup: the UI is usable in under a second, drawn from the last saved state. The first GitHub poll and resuming interrupted reviews happen in the background after that.
- What's there once Purr has started (its modules, Textual's, the first screen) is frozen out of the garbage collector's way (`gc.freeze`): a full collection went through all of it, about 100 ms, a freeze whenever one came along; now about 15 ms.
- A PR's transcript loads (in a thread) on first open, opens at its end, and stays cached.
- List rows are one line each and say so (`tui/rows.py`): Textual's list works out every row's height before drawing any, and a Rich table or rule has to be drawn to know it. With pipecat's 750 rows that took half a second each time the list was built (a repo opened, a poll's update) or changed width (the diff closed, `z`); now about a tenth of that.
- A poll that leaves the list's rows as they were (the same PRs, in the same order) draws again only the rows that look different, and the cursor and the scroll stay put (`PRList.show_options`); PRs coming, going or moving group build it again.
- Moving the cursor fast (a key held down), the PR's pane catches up at most every 100 ms (`PANE_EVERY`), and where the cursor stops; one key after a pause shows the PR at once. Showing a PR lays out the whole screen (its transcript and header are new), which costs as much as moving the cursor. The key bar is drawn again only when its keys change, since that too lays out the whole screen.
- Slow work (a poll, an agent turn) shows progress in place, and keys keep working meanwhile.

## Voice (planned)

Not built yet. The design:

- A Pipecat pipeline running in the same process with a local audio transport, activated by push-to-talk.
- It's a bus participant, so it can do anything the TUI can: list PRs, start reviews, read out summaries/findings, approve or dismiss pending actions, and send follow-ups into a PR's session.
- Proactive prompts: when `action.pending` arrives, the voice agent can ask e.g. "I've reviewed the message bus PR, three findings. Want me to post them and request changes?"
- Typing and talking should feel equivalent; voice is not a separate mode.
- Risky actions (merge, posting comments) require clear confirmation by voice too.
- "What did I miss?" reads out the news: what happened to which PRs since you last looked.
- It can answer the agent's permission prompts ("yes, let it run the tests").
- Navigation works by voice too: "go to whisker", "open the message bus PR", "go back".

## Configuration

Files follow the XDG convention: what you edit is in the config dir (`PURR_CONFIG_DIR`, else `$XDG_CONFIG_HOME/purr`, else `~/.config/purr`): `settings.toml`, your instructions (`review.md`, `code.md`, per repo under `repos/`), and the standing permissions you allowed per repo. What Purr manages is in the data dir (`~/.local/share/purr`): the database, the log, its clones and worktrees.

**Settings** (`config.py`) come from, each over the one before: their defaults, `settings.toml`, the environment (`PURR_DATA_DIR`), and command-line flags (`purr --help`, Typer as Pipecat's CLI: `--data-dir`, `--auto-review/--no-auto-review`, `--max-reviews`, `--permission-mode`, `--sandbox/--no-sandbox`; also `--headless`, `-v`, `--version`, and `purr login`, which only logs in to Claude). `settings.toml` can set any of them (but not where it is itself): `data_dir`, `poll_interval` (60 s), `auto_review`, `review_model` (Claude Code's default), `lead_model` and `quick_model` (Sonnet), `suggestion_model` (Haiku; empty: no suggestions), `review_budget_usd` (none), `permission_wait` (5 min), `max_reviews` (3), `up_next` (5; 0: none), `permission_mode` (`auto`), `sandbox`, `theme` (`solarized-dark`; one of Textual's). An empty value means none for those that can be none (`lead_model = ""`: Claude Code's default). It's read when Purr starts (a new `theme` applies at once, when you save it from `i` then `o`); a name it doesn't know or a value of the wrong type stops it with the file and the setting. `save_setting` changes one setting in the file, leaving the rest and its comments as they are (the theme picker keeps its choice with it).

Each setting's description is next to it in `config.py` (`_setting(..., about=...)`), and `i` then `o` makes the starter `settings.toml` from them, every setting commented out at its default, then opens it in Purr's editor, which checks it before it saves it, so a typo shows at once (and never reaches the file) rather than stopping the next start.
